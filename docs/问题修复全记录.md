# 第一部分 用户实测反馈的问题

## 1.1 早期实测反馈五项（提交 c5bed82）

**1-1　`.env`/manifest 泄露未选组件的账号密码**　【安全】
- 现象：只勾选部分中间件时，配置文件仍写入了未勾选组件的账号密码。
- 原因：凭据写入逻辑以"全量目录"而非"所选服务集合"为输入。
- 解决：`.env`/manifest 只含所选组件的凭据。
- 验证：多组勾选组合打包后逐文件核对。

**1-2　MongoDB 健康检查永远不通过**　【容器行为 / Shell】
- 现象：MongoDB 容器实际可用，健康检查始终失败。
- 原因：两层叠加——检查命令中 grep 关键字的引号写法**永远匹配不上**；且建库完成后 `ping` 需要认证，免认证探测必然失败。
- 解决：改为带账号认证的探测，并以退出码语义匹配结果。
- 验证：本机 Docker Desktop 实测容器转 `healthy`。

**1-3　PATH 缺 `/usr/local/bin` 的系统装完找不到命令**　【平台兼容】
- 现象：部分 Linux 发行版安装后 `docker compose` 等命令不可用。
- 原因：部署脚本把二进制放到 `/usr/local/bin`，但目标系统 PATH 不含该目录。
- 解决：脚本内即时补齐 PATH → 写入 `profile.d` 持久化 → 安装后自检失败时兜底软链到 `/usr/bin`。三级降级。

**1-4　选择中间件无"清空选择"**　【交互】：增加带已选数量的清空按钮。

**1-5　顶部步骤条样式生硬**　【交互】：改胶囊样式（后续 ca13280/3bde4a4 持续迭代为滑动指示胶囊）。

**1-19　点"下一步"直接进了预览打包**　【前端逻辑——弱类型陷阱】
- 现象：任意步骤点下一步直接跳到第 5 步（预览）。
- 原因：`curStep` 经 `gotoView(String(v))` 后保持**字符串**形态，`curStep + 1` 触发字符串拼接（`'2'+1='21'`），再被 `Math.min(5, '21')` 隐式转数值为 5。
- 解决：所有步进运算显式转数值 `+curStep + 1`。
- 验证：浏览器实测 1→2→3→4→5 逐步推进。
- 论文角度：JS 弱类型运算符重载（`+` 双语义）在状态机步进代码中的典型事故形态。

## 1.5 功能类反馈

**1-21　数据库配置文件要挂载出来，并内置 `sql_mode` 严格模式**（提交 54e6e9c）　【需求实现】
- 需求：MySQL 参数要能在宿主机改，且 `[mysqld]` 预置 `sql_mode=STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION`（8.0 默认值，显式声明统一 5.7/8.0 行为）。
- 实现：新增 `templates/mysql-my.cnf` → 打包落位 `conf/mysql8/my.cnf`、`conf/mysql57/my.cnf`（主从拓扑再各一份 replica）；compose 只读挂载 `/etc/mysql/conf.d/my.cnf`；deploy.sh 拷贝语义**不带"由打包器生成"标记** → `cp -an` 只补齐不覆盖，重新部署不会冲掉用户手改；落盘强制 644（见 2-6）。
- 验证：gen_compose 挂载断言、`docker compose config` 校验、真实打包 312MB 包解包核对 tar 内文件与内容逐字节一致。

**1-22　MySQL 5.7 部署后明明可用，仍提示健康检查未通过**（提交 20de28c）　【容器行为 / 数据库行为】
- 现象：库已可登录使用，deploy.sh 最终健康实测仍报超时失败。
- 原因（三层）：
  1. `health_check` 总窗口 180s（60 轮 × 3s），而低配/老机器上 MySQL **首次启动**需初始化系统表并临时起 server，实测可超 3 分钟——窗口小于真实初始化时间；
  2. compose 健康检查用 `mysqladmin ping` 免鉴权探测，MySQL 5.7 对 access denied 也返回 exit 0（假通过语义，见 2-7），健康状态与真实可用性脱节；
  3. 故健康状态常落后于"实际已能用"。
- 解决：① mysql 服务改**鉴权探活优先**——`docker exec -e MYSQL_PWD=... mysql -uroot -N -e "SELECT 1"` 通过即判 OK，不再等 compose 健康态；② 兜底 `wait_healthy` 轮次 60→100（300s 预算）；③ compose `start_period` 60s→300s；④ my.cnf 落盘 chmod 644（2-6 顺带修复）。
- 验证：`bash -n` 语法检查；gen_compose 断言；从物料仓库 tar 加载**真实** mysql:5.7.44 镜像起容器，提取 deploy.sh 中真身 `health_check/wait_healthy` 函数实测——正例输出 `OK|mysql57t|MySQL 鉴权探活通过(实测 SELECT 1)` 且 `HEALTH_BAD=0`，反例（假容器名）正确判 BAD。
- 论文角度：健康检查的"探针语义"问题——免鉴权 ping 只证进程在，鉴权 SELECT 才证服务可用；超时窗口应以**最慢合法路径**（首次初始化）而非稳态启动时间为准。

## 1.6 K8s 集群集成轮反馈（2026-09-30）

**1-23　整页点击瘫痪：顶部 tab 与全部按钮无响应**
- 现象：页面停留在首页，5 个步骤 tab 与所有按钮点击均无效。
- 原因：`renderWarehouse()` 引用了从未定义的 `cacheLabel`（物料仓库 K8s 物料改造的遗留引用），`init()` 执行到它即抛 ReferenceError，**其后的全部事件绑定（步骤 tab、生成预览、开始打包、物料仓库、保存/导入）均未执行**。
- 解决：补组件标签映射；用浏览器逐函数注入调用定位抛点（`renderWarehouse → cacheLabel is not defined`）。
- 教训（论文角度）：① `node --check` 语法通过 ≠ 运行时可用，未定义引用只能靠执行暴露；② UI 回归的断言必须读真实 DOM 状态——首轮回归的自拟选择器查了已被运行时替换掉的旧节点，得出假阳性"已修复"结论，被用户复测打回。
- 验证：初始化链全按钮绑定体检全 ok；5 tab 实点全切换。

**1-24　表单"另起一行且不对齐"、右侧大片留白**
- 现象：K8s 版本与 CNI 插件各占一整行（版本选择只有几个字却占满整行宽），且两行标签缩进不一致。
- 原因：`kfRow(l1,f1,l2,f2)` 四参语义实现错误——设计意图"一行左右两组"，实现却渲染为两个独立行；两组各自用 `.krow`(label 140px) 与 `.krow2`(label 120px)，缩进自然对不齐。
- 解决：kfRow 重写为真同行两组（flex 双 label+双 field）；基础/高级配置全部重排为两列对齐；表单容器 660→780px；提示行统一缩进挂字段下方。
- 验证：截图确认 K8s 版本|CNI 插件、Pod CIDR|Service CIDR、控制面 HA|kube-proxy 模式、时区|升级包同行对齐。

**1-25　徽标"要两行给三行"**
- 现象：集群卡片徽标 x86 与 110 MB 折成三行（110 与 MB 断开）。
- 原因：`<br>` 分行后 pill 容器过窄发生二次折行。
- 解决：徽标 `white-space:nowrap` 防内折。
- 验证：截图确认恰好两行。

**1-26　四个区块层级样式统一**
- 现象：集群角色分配/基础配置/高级配置为三种样式（ksec 小标题、无标题、自绘 summary），与"基础平台"不一致。
- 解决：三者统一为 `h3.cat-h`（与"基础平台"同款）；高级配置保留折叠但标题并入 summary。

**1-27　服务器池改名后角色分配标签不同步**
- 原因：别名/IP 输入只写 state 不刷新角色区；整区重渲染会打断输入焦点。
- 解决：`oninput` 就地更新对应角色行标签文本（不重渲染、不丢焦点）。
- 验证：输入"web-生产-01 · 10.0.0.1"即时同步。

# 第二部分 实机/自动化测试中自行发现并修复的缺陷

## 2.1 前端与浏览器自动化类

**2-1　`curStep` 字符串拼接 bug**　——即 1-19，系调试用户报告时自行定位到的根因，此处不重复计。同类教训：视图状态经字符串传递后，一切算术前先显式转数值。

**2-2　空徽标残留圆点**　【前端】：顶栏"物料仓库"徽标 `b.wbadge` 无缺失物料时仍渲染空内联元素，显示为一颗多余的点；补 `.wbadge:empty{display:none}`。教训：徽标类装饰元素必须处理空态。

**2-3　全局暂停动画注入冻结入场动画**　【自动化测试】
- 现象：为稳定截图注入 `*{animation-play-state:paused}` 后，抽屉等带入场动画的元素集体**隐身**（截图全空）。
- 原因：动画被冻结在第 0 帧，而入场动画第 0 帧为 `opacity:0`。
- 解决：注入规则豁免被测元素 `.dw,.dw-mask{animation:none}`。
- 论文角度：视觉回归测试中"稳定化手段"本身改变被测系统状态（观察者效应）的实例。

**2-4　内嵌浏览器渲染节流**　【自动化测试】：截图超时/取到旧帧、Playwright 点击 actionability 卡死，均为面板停止渲染所致；对策——重新激活可见性、必要时降级为坐标点击（CUA）、重载标签页。教训：自动化中的"元素明明存在却点不动"要先排除宿主渲染节流，再查选择器。

**2-5　CDP 自动化三个坑**　【自动化测试】（详见测试环境问题记录 #2）：页面 JS 包在 IIFE 内不可直调（改 DOM 事件驱动）；`captureScreenshot` 的 clip 对内部滚动容器截出空白（改 scrollIntoView+整屏）；`onclick=closeDrawers` 把 event 对象误当参数（箭头函数包裹）。

## 2.2 Shell 与代码生成器类

**2-6　MySQL 静默忽略"全局可写"的配置文件**　【容器/数据库行为】
- 发现过程：docker run 实验挂载 my.cnf 时，容器日志出现配置被忽略告警——MySQL 出于安全**静默跳过** world-writable 配置（Windows 挂载默认权限放大触发；真实服务器上 cp 保留源权限同样可能踩中）。
- 解决：deploy.sh conf 落盘循环内对 `*.cnf` 强制 `chmod 644`。
- 论文角度：**静默降级**类故障——无报错、无效果，只能靠对照实验（同一配置改权限前后行为差异）定位。

**2-7　`mysqladmin ping` 免鉴权假通过**　【数据库行为】
- 发现过程：排查 1-22 时设计对照实验发现——MySQL 5.7 下**密码错误**（access denied）时 `mysqladmin ping` 依然 exit 0。免鉴权探针只能证明 mysqld 进程存活，无法区分"拒绝服务"与"服务可用"。
- 解决：部署脚本一律改用鉴权 `SELECT 1` 探活（见 1-22）。
- 论文角度：探针分层模型——L1 进程在（ping）/ L2 端口通（/dev/tcp）/ L3 业务可用（鉴权查询），健康检查应至少做到 L3。

**2-8　`backup.sh` 轮转函数空目录误退出**　【Shell 语义】
- 原因：`ls 备份目录/*` 无匹配时 glob 原样输出且退出码非 0，叠加 `set -o pipefail` 导致整个备份流程在"首次运行（目录为空）"这一最常见场景直接失败。
- 解决：改用 `find` 实现（天然容忍空结果）。
- 论文角度：`pipefail`/`set -e` 严格模式与 glob 空匹配的组合陷阱——严格模式把"良性问题"放大为"流程中断"。

**2-9　代码生成器双重转义（POST_SQL 数组解析即崩）**　【代码生成 / Shell】（E2E 场景 S4 抓获，提交 d29547c）
- 现象：MySQL 多机节点的 install-node.sh 一执行就崩，主从复制建立失败。
- 原因：`gen_node_install_sh` 先对 `"cn|sql"` 列表 bash_quote，模板又 `" ".join(bash_quote(...))` 二次转义，生成的 `POST_SQL=(...)` 每个字符间被塞进空格——**逐字符 `repr(line)` 才定位到**。
- 解决：去掉一层转义；新增断言"含 SQL 内插的节点脚本必须过 `bash -n` 且数组单引号包裹"。
- 教训：`bash -n` 防线必须覆盖**每一种**含复杂内插的节点类型，而不是只测最简单的；双重转义类 bug 只有运行时或逐字节检查能暴露。

**2-10　节点侧 conf 目录桥接缺失**　【代码生成】（E2E 场景 S3 抓获）
- 现象：节点 compose 挂载 `./redis/redis.conf`，但文件实际还在 `conf/redis/` 下，真实部署会挂载成空目录导致容器起不来。
- 原因：主部署机 deploy.sh 有 conf 桥接逻辑，新生成的节点 install-node.sh 漏配。
- 解决：install-node.sh 补齐桥接 + 数据目录创建。
- 教训：同一逻辑在两处实现（主部署机/节点）时，E2E 必须两边都走到——单测只覆盖了主路径。

## 2.3 Docker/中间件真实行为类

**2-11　Kafka env 机制键被通用前缀覆盖**　【中间件行为】（提交 22f9c4a，真机验证发现）
- 现象：SASL 机制配置不生效。
- 原因：`KAFKA_LISTENER_NAME...SASL_JAAS_CONFIG` 这类**带连字符的机制级 env 键**被镜像原样保留、不参与 `KAFKA_` 前缀到 properties 的通用转换，4.x 对通用键的处理规则忽略了它们。
- 解决：机制级 JAAS 经 env 直传，deploy.sh 启动后再幂等注册 SCRAM 用户。
- 论文角度：镜像对环境变量的"约定式解析"并非全键覆盖，特殊字符键名需逐键验证。

**2-12　Kibana 9.x 禁止 elastic 超级用户运行**　【中间件行为】：启动即报错退出；改用 `kibana_system` 服务账号，deploy.sh 启动后自动置其密码（幂等）。

**2-13　kafka-ui 默认端口 18090 与 Kibana 冲突**　【端口规划】：同选两组件时端口冲突，kafka-ui 改 18092。教训：多组件端口分配必须有全局唯一性校验（打包器已有 `/proc/net/tcp` 端口预检与组件间冲突校验）。

**2-14　集群脚本 WSL2 systemd 环境逐包真机修复**　（提交 c786dd2）：集群形态脚本在 WSL2+systemd 环境逐包部署验证，暴露并修复多处在"无 systemd/最小化"环境下不适用的假设。

**2-15　MySQL 5.7/8.0 复制语法自动适配**　【中间件行为】（设计期规避，实测确认）：5.7 用 `CHANGE MASTER TO/SHOW SLAVE`，8.0 用 `CHANGE REPLICATION SOURCE TO/SHOW REPLICA`；打包器按目标镜像 VERSION() 自动生成对应语法，E2E S3/S4 双场景验证通过。

**2-16　伪 docker 垫片的调用语义混淆**　【测试基建】（测试环境问题记录 #8.2）：`docker inspect` 对镜像查架构、对容器查健康，垫片一律返回 `healthy` 导致镜像架构校验误报不符。教训：替身（shim）必须区分调用语义，否则上游校验逻辑被误触发。

**2-17　Git Bash 调 Docker 的 MSYS 路径转换**　【工具链】（测试环境问题记录 #3）：容器内绝对路径 `/var/log/...`、`/bundle` 被改写为 Windows 路径，曾致容器 `--log-error` 指向 `D:/Git/var/...` 直接启动失败；一律加 `MSYS_NO_PATHCONV=1`。

**2-22　打包报 `cannot access local variable 'total_bytes'`**
- 原因：`total_bytes` 的赋值被写进集群分支内部，纯中间件包不经过该分支即未赋值先使用。
- 解决：移出分支统一计算；冒烟回归补齐两种形态。

**2-23　kk artifact export 端到端六连坑（打包时自动构建产物）**
- ① **CLI 参数**：kk v4 的 `artifact export` 用 `-a` 而非 `-o`，原 .bat 一执行即 `unknown shorthand flag: 'o'`；
- ② **挂载路径**：.bat 把 artifact 目录挂成 /work 却引用 /work/kk/...（kk 实际在 warehouse/cluster/kk/）——加第二只读挂载修正；
- ③ **容器无 sudo**：kk 本地连接器固定 `sudo -SE` 执行命令，ubuntu 容器无 sudo 且官方 apt 源 503 装不上 → 写 sudo 垫片（`sudo -SE cmd` 透传执行）+ 假 /etc/sudoers + 假 visudo（导出 playbook 的 native/root 角色要备份/校验/改写 sudoers）；
- ④ **配置缺 `fetch: true`**：kk 对未设置的 `download.fetch` 默认置 false，download 角色整体跳过，后续 "Ensure xxx is present" 校验必失败；
- ⑤ **网络与证书**：github 直连 TLS 超时 → 配置 `zone: cn` 走青云国内源（kk 内建）；镜像源又因容器无 CA 证书 x509 失败，而 https apt 源装证书是死循环 → apt 源先用 http（华为云）装 ca-certificates；
- ⑥ **产物落点**：kk 固定输出 `{workdir}/artifact/kubekey-artifact.tgz`，`-a` 并不控制输出路径 → workdir 设在挂载盘 /work/kkstage，导出后搬运改名到 warehouse/cluster/artifact/ 并清理暂存。
- 结果：72 任务 0 失败、产物 93MB；打包流水线内自动构建端到端跑通（133MB 集群包，cluster=true，sha256 齐备）。
- 论文角度：一次"文档没有写的能力"逆向——六个坑横跨 CLI 语义、容器化执行环境、上游默认值、网络策略、PKI 引导、产物契约；每一步都由"看真实报错 → 对照源码（builtin playbook 与连接器实现）→ 最小修正"闭环。

**2-24　prepare_cluster.py 根锚点错一层**
- 原因：脚本从 k8s/ 合并到仓库根后 `BASE_DIR = parent.parent` 未更新，`--artifact-export` 直接 `FileNotFoundError(E:\project\versions.json)`，模块被导入时的物料路径也全部偏移。

- 验证：`--check` 盘点全绿、路径全部正确；`--artifact-export` 正常生成配置与一键脚本。

**2-25　真机纯离线部署五连根因（v1.28.15+flannel, CentOS7 3.10 内核, 2026-10-01）**
- 背景：离线包部署真机(10.100.11.112/113)反复卡在节点 NotReady / wait-control-plane 超时，
  最终定位为"包是离线的、镜像却在线拉"的混合模式，连根拔除后一次通过：双节点 Ready、
  12 个 Pod 全 Running、componentstatuses 全 Healthy。
- ① **containerd 配置跳过坑**：kk 的 cri 角色在"二进制版本已匹配 && config_policy 为空"时
  连配置写入带服务重启整块跳过 → 节点带着默认配置跑（sandbox=registry.k8s.io/pause:3.8 未导入
  → 沙箱创建联网拉取超时 → 全部静态 pod 起不来）。修法：packer 发 `config_policy: overwrite`
  让 kk 每次重写配置并重启（镜像落在 data_root 磁盘存储，重启不丢）。
- ② **etcd 镜像 library 规范化**：kubeadm 请求 `docker.io/etcd:v3.5.15`，containerd 规范化为
  `docker.io/library/etcd` 再查本地 → 导入 tag 少了 library 全部 miss 后转在线拉取。
  规范：镜像清单一律写 `docker.io/library/` 全称。
- ③ **flannel 镜像源误判**：chart 0.27.4 实际用 `ghcr.io/flannel-io/flannel:v0.27.4` 与
  `flannel-cni-plugin:v1.8.0-flannel1`（kk values 只覆写 repository 前缀, tag 跟随 chart），
  之前按 docker.io/flannel 准备的镜像全部无效。
- ④ **NodeLocalDNS 默认启用**：clusterDNS=169.254.25.10 → `registry.k8s.io/dns/k8s-dns-node-cache`
  必须随版本离线导入（versions.json 全 15 版本补 nodelocaldns_tag/coredns_tag 对照表）。
- ⑤ **localpv 存储类默认启用**：kk v1.28 defaults `storage_class.local.enabled=true`，包内没有
  localpv chart 时会折在存储类步骤 → packer 显式输出 storage_class（不依赖上游静默默认）。
- 配套产品化：`k8s_image_specs`（按版本精确推导镜像清单单一来源）+ `ensure_images`（docker
  国内源 pull→retag 原生→save）+ deploy-cluster.sh【集群 3.5】节点镜像导入（含残留 kubelet
  unit 守卫）+ 升级脚本带目标版本镜像导入与 sandbox 改写。
- 论文角度：**"离线"必须端到端审计**——二进制离线不等于镜像离线；五个根因全部是"组件各自
  带默认值"的叠加（containerd 默认配置、kubeadm 默认镜像源、chart 默认 registry、kk 默认开关、
  containerd 引用规范化），任何一层单独看都"合理"。防御方式：部署完成后审计 ctr images ls
  与节点访问日志，任何非本地命中的拉取都视为离线性破坏。

# 第三部分 已知限制（未修复，论文"局限性与展望"素材）

**3-1　老 CPU（不支持 x86-64-v2）无法运行部分新版官方镜像**
- 现象：老服务器部署 MySQL 8.0.46、新版 MinIO 报 `Fatal glibc error: CPU does not support x86-64-v2`。

- 论文角度：离线分发系统对"镜像—CPU 微架构兼容矩阵"的管理责任：官方镜像的基线指令集随上游基础系统升级而抬升，物料仓库需记录每个 tar 的构建基线。

# 第四部分 方法论沉淀（论文"讨论"节素材）

1. **失败分类学**：所有失败严格归为三类——产品 bug / 测试代码 bug / 环境问题（本项目中三者比例约为 40 条 vs 若干 vs 8 类）。判定准则：**同一失败点手动复现正常即可归因为环境**；环境不许背产品 bug 的锅，产品也不为环境抖动改代码。本轮两类误判都出现过（S4 双重转义是真 bug，VM 崩溃是环境）。
2. **幂等设计的环境对冲价值**：deploy.sh/distribute.sh 全部幂等可重跑，Docker Desktop VM 六次崩溃后均能"重启引擎 → 幂等重跑"恢复，环境抖动未损失任何测试进度——幂等不仅是运维特性，更是**长周期测试的容错基座**。
3. **探针分层模型**：进程在（ping）→ 端口通（/dev/tcp）→ 业务可用（鉴权查询）。免鉴权健康检查的假通过/假失败双向事故（2-7、1-22）证明健康检查必须做到 L3。
4. **静默降级是最高危故障形态**：MySQL 忽略可写配置（2-6）、Kafka 忽略机制键（2-11）、glob 空匹配（2-8）共同特征是"无报错、无效果"，只能靠对照实验与逐字节检查定位；系统设计应**宁可显式报错，不做静默跳过**。
5. **代码生成器的防线覆盖度**：`bash -n` 必须覆盖每一种含复杂内插（SQL/密码/引号）的生成产物类型；双重转义 bug 只能靠运行时或 `repr` 逐字节检查暴露（2-9）。
6. **"改了代码测的是旧东西"双坑**：残留旧服务进程（测试环境问题记录 #1）+ 浏览器缓存旧页面（2-20）——每轮改码后测试前的标准动作：清旧实例、响应禁缓存。
7. **环境即代码**：测试环境全部物料（Dockerfile/垫片/场景 json/配置）入库，Docker Desktop 自毁 WSL 发行版后 **10 分钟重建**全部测试矩阵（测试环境问题记录 #6）——容器内不存唯一状态。
8. **视觉回归的观察者效应**：截图稳定化手段（暂停动画）本身改变被测系统（2-3）；自动化工具链的每个"稳定化技巧"都需验证其不改变语义。

## 2-29 追记: 卸载验证连环暴露两个潜伏产品 bug(均由真机自动化链路触发)

1. **RUN_SCP 用了 ssh 的端口参数**: deploy-cluster.sh 两处与 upgrade-cluster.sh 模板的
   `RUN_SCP() { ... scp $SSH_OPTS }` 共用了含 `-p $SSH_PORT` 的 SSH 选项 — ssh 端口是
   小写 -p, **scp 是大写 -P(-p 是保留时间戳)**。scp 把 "22" 当成源文件, rc=1 且什么都不拷:
   OS 依赖包分发与"镜像 tar 分发到非本机节点"全部静默失败(prep_one_node 的 `|| return 1`
   无日志)。此前未暴露: 真机部署镜像导入走的是本机 cp 分支, 只有第二节点 scp 路径会踩。
2. **非登录 shell PATH 缺 /usr/local/bin**: cron/CI/paramiko exec 等以非登录 shell 跑
   deploy-cluster.sh 时, 3.5 步预装的 containerd(装在 /usr/local/bin)在下一步
   `containerd config default` 处 command not found。deploy-cluster.sh 只在第 5 步才
   export PATH。修复: deploy/upgrade 脚本头部统一 `export PATH="/usr/local/bin:/usr/local/sbin:$PATH"`。

教训: "只在交互登录 shell 里测过"的部署脚本, 自动化(无人值守)场景必挂 — PATH 与

## 10-01 追记: online+cn 国内源链路产品化 + 中间件真实运行时矩阵(真机/Docker 实测暴露)

背景: 用户指出"online 模式需节点外网不成立, 国内也有镜像源", 并追问"中间件全部测好了吗"。
实测发现 e2e-docker 报告的分发链路用的是伪 docker 垫片, 20 个中间件没有一个真实
compose up 过; online 模式也从未真机跑过。本轮四条链路全打通。

1. **online+cn static containerd 404 (真机首踩)**: 国内二进制源 kubekey.pek3b.qingstor.com
   只同步非 static 版 containerd, 而包配置默认 `static_binary: true` → kk 拼 URL 变成
   `containerd-static-*` 404。修复: packer.validate_config 对 online+zone=cn 自动回退
   static_binary=false 并双语告警(cache/离线与国际源保留 static)。回归:
   test_cluster_lifecycle.test_online_cn_static_fallback。
2. **online+cn 裸域名 imageRepository 丢命名空间**: 生成配置曾写
   `registry.imageRepository: hub.kubesphere.com.cn`, kubeadm 据此拼出
   `hub.kubesphere.com.cn/etcd` → hub 400。hub 真实路径是 `kubernetes/etcd`
   (registry 匿名 token 探针逐一定位)。修复: online+cn 不写该覆盖也不覆盖 sandbox,
   交给 kk 内置 CN 映射(kubernetes/*、coredns/coredns、flannel-io/*)。回归:
   gen_cluster_config 断言 imageRepository/sandbox 不出现。
3. **kk 上游 bug: kubeadm etcd imageRepository 丢 kubesphere/ 命名空间**:
   kubeadm-init 模板 `etcd.local.imageRepository: {{ .etcd.image.registry }}` 只取 registry
   (kubeadm 自行追加 /etcd), defaults 里 repository=kubesphere/etcd 被整体丢弃 →
   CN 源拼出 hub.../etcd、国际源拼出 docker.io/etcd(恰好存在, 故上游未暴露)。
   修复 builtin/core/roles/defaults/defaults/main/04-etcd.yaml: CN→`k8sio_registry/kubernetes`
   (hub 托管 kubernetes/etcd), 国际保持 docker.io。重建 kk v4.0.7-xc1 换入 warehouse。
4. **镜像 tar 仓库名三形态 + retag-mirrors.sh**: 仓库镜像 tar 实测三种形态——
   `nginx:1.31.5-amd64`(架构后缀)/`docker.1ms.run/library/rabbitmq:4.3.5`(镜像源+library)/
   `docker.1ms.run/apache/kafka:4.3.1`(镜像源前缀)。离线机 compose 按原生短名取镜像,

   install-node.sh 完全没有**)。修复: packer 生成 `images/retag-mirrors.sh` 随包
