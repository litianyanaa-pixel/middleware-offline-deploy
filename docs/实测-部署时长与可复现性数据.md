## 1. 结果总览：人工 vs 工具对照

| 维度 | 单机 MySQL8+Redis | 多机 MySQL8 主从(1主1从) |
|---|---|---|
| **人工部署用时** | **30 分钟** | **≈60 分钟** |
| **工具部署用时** | 服务器侧 **56s**; 含打包上传全链路 3.5min | 服务器侧 **161s**; 含打包上传全链路 7.7min |
| **提速比** | **≈32 倍**(服务器侧口径) / ≈8.6 倍(全链路口径) | **≈22 倍**(服务器侧口径) / ≈7.8 倍(全链路口径) |
| **操作步骤数** | 人工 20 步 → 工具 **4 条命令** | 人工 23 步 → 工具 **3 条命令**(仅主部署机) |
| **过程错误次数** | 人工 3 次 → 工具 **0 次** | 人工 4 次 → 工具 **0 次** |
| **跨机登录次数** | — | 人工需 SSH 登录从节点配置复制; 工具 **0 次**(distribute 自动分发) |
| 可复现性 | 工具: 同配置 3 次打包产物逐字节一致, 卸载→重装报告仅时间戳一行之差 | 工具: distribute 幂等重跑 51.8s 全过 |

> 口径说明: "服务器侧" = 离线包已在服务器上, 从解压到服务可用(人工操作也以在服务器上的
> 操作为主); "全链路" = 打包 + 上传 + 部署。人工用时为实验者端到端记录, 含其在服务器上的
> 全部手工操作与排错时间。

## 2. 单机 MySQL8 + Redis：工具侧全链路计时明细

配置: mysql8(23306) + redis(23379), 包 363MB, deploy_dir=/data1/mwbench1。

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 打包(本地 Windows) | **34.3s / 34.7s**（两轮实测; 首轮 ≈35s） | 含 sha256 生成 |
| 上传 363MB | **154.0s**（2.4 MB/s） | scp + 随包 .sha256 |
| 服务器解压 tar | **8.8s** | |
| `./deploy.sh`（冷, 9 步） | **46.7s** | 明细见下 |
| **服务器侧合计(解压→可用)** | **≈56s** | 探针通过即服务可用 |
| **全链路合计(打包→可用)** | **≈210s (3.5min)** | |

deploy.sh 冷部署内部（首轮, 逐行时间戳）:

| 步骤 | 耗时 |
|---|---|
| 【1-2/9】Docker/Compose 检测（已装跳过） | <1s |
| 【3/9】加载离线镜像(818MB+138MB) | 14s |
| 【4-5/9】磁盘端口预检 + 部署目录 | <1s |
| 【8/9】docker compose up | 16s |
| 【9/9】健康实测（mysql 鉴权探活 + 容器健康） | 15s |

部署后探针（自动化）: mysql8 `SELECT VERSION()=8.0.46` ✓ · redis `PONG` ✓ · 双容器 healthy ✓ ·
部署报告自动生成（服务清单/健康结果/运维命令/账号位置/备份计划五节）✓

#### 人工部署同场景分段（对照 · 实验者实测）

总时长 **30 分钟**, 操作步骤 **20 步**, 过程错误 **3 次**:

| 阶段 | 耗时(整理值) | 步骤 | 人工操作内容 |
|---|---|---|---|
| 环境准备 | ≈8min | 4 | 传输并安装 Docker/Compose、编写 daemon.json(数据目录/日志轮转/开机自启) |
| 镜像就位 | ≈4min | 2 | 传输 mysql/redis 镜像 tar、`docker load` 并核对架构 |
| 编排与配置编写 | ≈9min | 6 | 手写 docker-compose.yml(mysql8+redis 双服务: 端口/密码/挂载/健康检查/重启策略)、redis.conf、my.cnf、.env |
| 启动与排错 | ≈6min | 4 | 启动容器、逐一处理报错(3 次过程错误的定位与纠正在此段及相邻配置段间进行) |
| 健康验证与收尾 | ≈3min | 4 | mysql 连通 / redis PING / 自启策略 / 日志轮转逐项人工核验 |
| **合计** | **30min** | **20 步** | **过程错误 3 次**(实验者实测记录) |

> 人工分段口径: 总时长/步骤数/错误次数为实验者实测; 各阶段耗时为按标准 runbook
> 步骤归类的整理值(合计=实测总时长), 错误纠正时间摊入相关阶段。

> 重装口径: 镜像层已在本地时 deploy.sh 仅 **15.6s**（docker load 层复用）。
> 人工对照实验区分"冷机首次"与"重装"两种口径分别计时。

## 3. 多机 MySQL8 主从（1 主 1 从跨机）：工具侧全链路计时明细

配置: mysql8 一主(112:24330)一从(113:24331) + redis(112:24379), 包 583MB（mysql 镜像随两节点各带一份）。
**运维只登录主部署机一次, 113 全程零登录**（distribute.sh 自动 SSH 分发安装）。

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 打包 | **60.1s** | 583MB |
| 上传到主部署机 | **302.3s**（1.9 MB/s） | 仅上传一处(节点包由 distribute 分发) |
| 服务器解压 | **15.5s** | |
| `./deploy.sh`（主部署机 redis） | **17.4s** | |
| `./distribute.sh`（双节点安装+复制建立） | **128.4s** | 明细见下 |
| **服务器侧合计(解压→主从可用)** | **≈161s** | 复制追平另需 ≤10s |
| **全链路合计** | **≈464s (7.7min)** | |
| 复制追平(从库回放完主库 binlog) | **≤10s** | Seconds_Behind_Source→0 |

distribute.sh 内部：

| 节点 | 步骤 | 耗时 |
|---|---|---|
| mw112(主库, 本机节点) | 镜像加载 15s + 启动 7s + 健康等待 27s + 鉴权等待 <1s + 建复 账号 SQL 1s | ≈50s |
| mw113(从库) | tar 管道分发 38s + 镜像加载 17s + 启动 6s + 健康 10s + 鉴权等待 7s + 复制 SQL | ≈79s |

复制取证（自动化探针）:
- `Replica_IO_Running: Yes` / `Replica_SQL_Running: Yes` ✓
- 主库写入 benchrepl.t1 两行 → 从库 **10 秒内**读到 `COUNT=2` ✓
- 端到端再写 id=3 → 从库(server_id=10)读到 1/2/3 全部三行 ✓
- 从库写保护: `CREATE DATABASE` 被 **super-read-only 拒绝**(ERROR 1290) ✓

#### 人工部署同场景分段（对照 · 实验者实测）

总时长 **≈60 分钟**, 操作步骤 **23 步**, 过程错误 **4 次**（需 SSH 登录两台机交替操作）:

| 阶段 | 耗时(整理值) | 步骤 | 人工操作内容 |
|---|---|---|---|
| 双机环境准备 | ≈12min | 5 | 两台机分别传输安装 Docker/Compose、daemon.json、开机自启(×2 交替) |
| 镜像准备与分发 | ≈8min | 3 | 主/从节点分别传输并 `docker load` mysql 镜像, 主机另 load redis |
| 编排与配置编写 | ≈12min | 5 | 手写主/从 compose、my.cnf×2、redis.conf、.env(端口/密码/挂载, 主从参数不同不能复制粘贴了事) |
| 主库初始化 | ≈6min | 3 | GTID/binlog 参数核对、启动主库、建 repl 复制账号并授权 |
| 从库复制接入 | ≈10min | 4 | CHANGE REPLICATION SOURCE(8.0 语法)、START REPLICA、查复制状态与排错 |
| 只读加固与复制验证 | ≈5min | 2 | super_read_only 置位、主写从读端到端验证 |
| Redis 与整体验证 | ≈7min | 1 | redis 启动接入、全链路健康核验 |
| **合计** | **≈60min** | **23 步** | **过程错误 4 次**(实验者实测记录) |

> 人工分段口径: 总时长/步骤数/错误次数为实验者实测; 各阶段耗时为按标准 runbook
> 步骤归类的整理值(合计=实测总时长), 错误纠正时间摊入相关阶段。
> 工具侧对应链路(§3 上表)不含任何人工决策: 同样的七个阶段被 deploy.sh 与
> distribute.sh 固化为 3 条命令, 从节点零登录。

## 4. 操作步骤数对照

redis.conf/my.cnf、设双密码、主库开 GTID/binlog、建 repl 账号、从库 CHANGE REPLICATION
SOURCE、super_read_only 置位、数据目录与属主、restart 策略、日志轮转、防火墙、逐服务验证。

## 7. 本轮真机抓取并修复的 2 个产品缺陷

独立详档: **`docs/缺陷修复-真机基准测试两例.md`**(现象/根因/定位过程/修复/验证全记录)。

1. **install-node.sh 缺 MySQL 真实鉴权等待**(严重, 多机主从必现): mysqladmin ping 健康
   检查在首启初始化临时 server 阶段误报 healthy → POST_SQL 撞初始化窗口 Access denied,
   复制建立失败。修复: POST_SQL 前逐容器 SELECT 1 探活等待。
2. **distribute.sh 本机节点被误导性跳过**: SSH 预检先于本机判断, 部署机未配自身免密时
   本机节点被跳过。修复: is_local_ip 分支前置。

附带观察(未改码): retag 后 `-amd64` 源 tag 残留, rmi 短名不回收层空间。

回归: `pytest tests/` 76 passed, 1 skipped; 修复后真机复测全链路一次通过。
