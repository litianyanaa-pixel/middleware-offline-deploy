## 缺陷 1: install-node.sh 缺 MySQL 真实鉴权等待（严重 · 多机主从场景必现）

| 项 | 内容 |
|---|---|
| 现象 | distribute.sh 安装 MySQL 从库节点时, 建 `repl` 复制账号的初始化 SQL 报 `ERROR 1045 (28000): Access denied for user 'root'@'localhost' (using password: YES)`, install-node.sh 中止, **主从复制关系建立失败**; 且时隐时现——mw113 第一轮安装失败, 第二轮却成功 |
| 影响面 | 所有"多机部署 + MySQL 主从"的节点安装(multihost mysql8/mysql57); 单机部署不受影响(主链路走 deploy.sh 另一条路径) |
| 根因 | compose 的 MySQL 健康检查 `mysqladmin ping -h localhost` 在**首次启动初始化的临时 server 阶段**(网络未开、root 密码尚未设置)就会返回存活——节点脚本看到 healthy 立即执行 POST_SQL(建 repl 账号), 此刻真实 root 还不可用, 必然 Access denied。"时隐时现" = 初始化快慢的竞态: 第二轮 mw113 的初始化恰好在健康判定前完成, 侥幸通过 |
| 定位过程 | distribute 输出只给到"等待容器健康(最长 10 分钟)…安装脚本执行失败", 无失败行; 上节点 `bash -x ./install-node.sh` 逐行 trace, 看到健康等待仅 3 轮即 break(healthy), 紧接着 POST_SQL 的 `docker exec … mysql -uroot` 报 1045 —— 失败点根本不在健康等待, 而在其后的 SQL 段; 对照手动连库(密码本身正确, `SELECT 1` 可通)排除密码错误, 锁定"探针语义"问题: ping 探活 ≠ 鉴权可用 |
| 为什么主链路没这问题 | deploy.sh 早有 `wait_mysql_ready`(真实 `SELECT 1` 鉴权探活, 100×3s)——此前单机轮就为同一坑建过防护; **多机节点脚本漏了同一防护**, 属"同一教训在第二个生成入口复发" |
| 修复 | `packerlib/multinode.py` gen_node_install_sh: POST_SQL 执行前对涉及容器逐个做真实鉴权探活等待(`docker exec … mysql -uroot -N -e "SELECT 1"`, 100×3s), 超时 die 并指引 `docker logs <cn>` 排查; 同容器多段 SQL 去重等待 |
| 验证 | 真机复测: 双节点全部安装成功, 复制 `Replica_IO_Running/Replica_SQL_Running = Yes`, 主库写入 ≤10s 从库追平可见, 从库 super_read_only 拒写; distribute 幂等重跑 51.8s 通过 |

**方法论**: 健康检查的"探针分层"——L1 进程在(ping)/ L2 端口通 / L3 业务可用(鉴权查询)。
凡"检查通过后立刻执行依赖该服务的写操作"的链路, 检查必须做到 L3; mysqladmin ping
在 MySQL 官方镜像首启初始化期间误报存活是已知陷阱, 防护必须随代码路径复制, 不能
只修"出事的那条路"。

## 缺陷 2: distribute.sh 本机节点被误导性跳过（中 · 特定环境触发）

| 项 | 内容 |
|---|---|
| 现象 | 主部署机本身也是集群节点时, distribute.sh 对其报"SSH 连接失败或未安装 Docker, 已跳过", 本机节点未安装; 提示语把人引向"没装 Docker"的错误方向 |
| 影响面 | 部署机未给**自己**配 SSH 免密(root 的 authorized_keys 无自身公钥)的所有多机部署; 上一轮多机真机验证未暴露, 是因为当时环境恰好配过自身免密——环境掩盖了缺陷 |
| 根因 | 预检顺序错误: 对每个节点先做 SSH 预检、后判 is_local_ip; 本机节点也要过 SSH 自连, root 未给自己发免密时必败, 于是被 continue 跳过 |
| 修复 | `packerlib/multinode.py` gen_distribute_sh: is_local_ip 分支前置——本机节点只检查本机 `command -v docker`, 不再要求自 SSH; 远端节点保持原 SSH 预检 |
| 验证 | 112 未配自身免密状态下(已回退临时配置), distribute.sh 本机节点"就地安装(免传输)"直接成功 |

## 附带观察（记录, 未改码）

- 镜像源 retag 归一化后, 源 tag(如 `mysql:8.0.46-amd64` 架构后缀形态)残留在节点本地;
  `docker rmi <短名>` 只 Untag 不回收层空间, 测试清场需短名+源 tag 同删(两 tag 一起 rmi
  才真正删层)。可考虑 retag-mirrors.sh / deploy.sh normalize_image 在归一化成功且源引用
  ≠ 短名时顺手 `docker rmi` 源引用。
- 测试环境教训: 前一场景的容器/镜像未清干净会污染下一场景的探针(容器名同名互指),
  每轮实验前应做"容器/镜像/端口/目录"四项零残留断言。
